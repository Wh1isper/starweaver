# Desktop and Runtime Configuration Reload

Status: typed host config, Desktop safe editing, backend-owned application preferences, and managed binary selection implemented; supervisor-fenced restart-required config activation remains planned

Starweaver Desktop has one long-lived RPC host per execution domain. Configuration must therefore change without starting one process per workspace, while active runs remain bound to the exact materialization under which they were admitted.

This document separates Desktop application configuration, immutable RPC bootstrap configuration, and reloadable RPC runtime configuration. It defines typed editing and explicit reload commands for local and SSH-hosted domains.

## Goals

- Desktop can display and edit its own safe application settings.
- Desktop can display and edit the safe, supported portion of each RPC host's runtime configuration.
- External edits to authoritative config files can be reloaded explicitly.
- Reload is atomic, generation-aware, idempotent, and safe while multiple sessions/runs exist.
- Active runs never observe a partially updated configuration.
- Bootstrap-only changes are reported as restart-required rather than partially applied.
- Provider credentials, transport secrets, private endpoints, and unrestricted paths never enter renderer state.

## Configuration Planes

| Plane                      | Owner                                                                | Examples                                                                                                                     | Activation                                                         |
| -------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Desktop application config | Desktop privileged backend                                           | UI preferences, recent workspace IDs, window behavior, non-secret SSH profiles, runtime channel/pin, update policy           | Desktop snapshot reload; selected fields may require shell restart |
| RPC bootstrap config       | Launch schema owned by RPC; instance generated by Desktop supervisor | execution-domain/database identity, state/runtime-config location, transport mode, capability ceilings, bootstrap generation | Immutable for one process; host restart required                   |
| RPC runtime config         | `starweaver-rpc`                                                     | default profile, profiles, model/provider declarations, tool policy, subagents, MCP/environment catalog, run policy          | Atomic host snapshot reload; some fields stage a restart           |

These generations are distinct:

- `desktopConfigRevision` identifies Desktop application configuration;
- `bootstrapConfigurationGeneration` identifies the immutable launch envelope used by one host process;
- `runtimeConfigRevision` identifies the RPC desired/active runtime configuration.

The generic name `configurationGeneration` must not be reused across these planes.

## Desktop Application Config

Desktop stores one owner-private, versioned application config under its platform application-support directory. It does not store canonical session evidence or provider credentials.

Initial safe fields may include:

- theme, locale, density, and notification preferences;
- window-close and background-residency behavior;
- recent opaque workspace IDs and display metadata;
- retained temporary-workspace policy;
- non-secret SSH profile routing and trust references;
- local and per-remote-domain runtime channel or exact pin;
- update approval and restart policy;
- bounded diagnostic-retention settings; and
- the last observed runtime-config revision for each execution domain.

Workspace canonical roots, SSH secrets, endpoint authenticators, model credentials, tokens, raw environment values, and RPC private diagnostics are not renderer-readable Desktop config fields.

### Desktop Commands

The native application boundary provides closed typed commands equivalent to:

- `desktop.config.get`
- `desktop.config.validate`
- `desktop.config.update`
- `desktop.config.reload`

These are Tauri application commands, not `starweaver.host` methods.

`desktop.config.reload` rereads only the application config path selected at Desktop startup. It never accepts a renderer-provided path. Reload performs a bounded regular-file/no-follow read, strict schema parse, semantic validation, immutable snapshot construction, and atomic snapshot swap. Failure keeps the last-known-good snapshot and returns bounded typed issues.

`desktop.config.update` uses an expected revision and idempotency key. The backend writes an owner-only same-directory temporary file, flushes it, atomically replaces the destination, syncs the parent directory where supported, then publishes the new snapshot. A stale expected revision returns a typed conflict and never overwrites a newer edit.

Desktop hot fields take effect immediately. Fields that change runtime selection, application data root, single-instance transport, or another bootstrap identity are staged and reported as `restart_required`.

## RPC Runtime Config Ownership

The RPC host is the authoritative parser, validator, persister, and publisher of runtime configuration.

Standalone mode may use the host-local `rpc.toml` selected at process startup. Desktop-supervised mode uses one RPC-owned managed runtime-config document whose location is fixed by the launch envelope. Desktop does not parse or directly write either file.

Desktop may configure the host only through typed `starweaver.host` operations. This preserves the boundary that `rpc.toml` is not a Desktop integration API and lets local and remote hosts apply identical validation and persistence rules.

The workspace registry is host-owned, owner-private persistent state but is not part of the static runtime config document or canonical session database. Dynamic workspace register/list/remove operations have their own typed protocol and durable identity; only explicit registration creates authority, and historical session paths never recreate a grant. Registry format v3 stores each mutation's exact safe result snapshot, so replay returns the original label, revision, and state even after later revoke/reactivate changes or loss of the original root; old receipt formats that cannot prove an exact result fail closed. Runtime config controls policies applied to workspace/session/run materialization; it does not contain arbitrary renderer-authored workspace paths.

## Runtime Config Revision

```text
RuntimeConfigRevision {
  generation: DecimalU64,
  etag: opaque ConfigEtag
}
```

Rules:

- RPC allocates and durably persists monotonically increasing generations.
- A process restart does not reset the generation to zero.
- `etag` is an opaque compare-and-swap token over the canonical validated declaration, not a client-computed digest.
- Credential values, provider tokens, dynamic sessions, and resolved secret environment values do not participate in the etag.
- Every response returns both `desiredRevision` and `activeRevision`.
- They are equal after a hot update. They differ while a restart-required candidate is staged.

## Required Host Methods

The canonical host IDL adds six methods. All params/results are closed schemas with `additionalProperties: false`.

### `config.get`

Returns:

- runtime config schema identity;
- source kind: `managed` or `rpc_toml`;
- desired and active revisions;
- safe runtime config projection;
- `current`, `restart_required`, or `source_invalid` state;
- bounded restart-required categories; and
- an optional safe diagnostic reference for the last failed reload.

The safe projection never contains raw TOML/JSON, config paths, credential values, token-file contents, private MCP headers/environment/commands, envd credentials/endpoints, or unrestricted filesystem paths. Sensitive declarations project at most a reviewed category and `configured: true`.

### `config.validate`

Parameters contain:

- `expectedEtag`;
- one closed typed runtime-config patch; and
- intent: `apply_if_hot` or `stage_if_restart_required`.

Validation is side-effect-free. It performs structure, references, capability ceilings, size limits, semantic consistency, and hot/restart classification without writing files, opening another database, starting a process, accessing the network, or resolving credential values.

The result is `unchanged`, `hot`, or `restart_required` and returns bounded stable field/category IDs plus safe warnings. Validation errors use bounded typed issues and a diagnostic reference; they do not echo raw secret-like input.

### `config.update`

Parameters contain:

- `expectedEtag`;
- a durable idempotency key owned by the privileged backend;
- one closed typed runtime-config patch; and
- restart policy: `reject` or `stage`.

Under one domain-wide config-writer lock, RPC:

1. checks the expected etag;
2. applies the patch to the desired declaration;
3. performs full validation again;
4. constructs every fallible derived catalog/snapshot object;
5. classifies the complete candidate;
6. atomically persists and publishes it, or stages the whole candidate for restart; and
7. returns a durable mutation receipt.

A hot candidate is committed as one complete immutable snapshot. A restart-required candidate with policy `stage` changes desired state but leaves the entire active snapshot unchanged. RPC never applies only the hot subset of a mixed candidate. Policy `reject` leaves both revisions unchanged.

Retrying the same idempotency key and fingerprint returns the original result. Reusing the key with another patch conflicts. A stale etag returns typed `configuration_conflict` data containing only the current desired revision and reconciliation requirement.

### `config.reload`

`config.reload` rereads the single authoritative runtime-config source bound at host startup. It accepts no path and no raw document.

Parameters contain:

- mode: `validate` or `commit`;
- `expectedEtag` for the current desired revision;
- the validated `candidateEtag` when committing;
- a durable idempotency key owned by the privileged backend when committing; and
- restart policy: `reject` or `stage`.

RPC performs a bounded regular-file/no-follow read, strict parse, validation, and classification. `validate` returns the candidate etag and safe changed categories without writing or publishing. After independent native confirmation, `commit` rereads the source, requires the same candidate etag, and runs the atomic publish/stage transaction used by `config.update`. An invalid, unreadable, or changed source keeps the last-known-good desired and active snapshots. Reload never falls back to defaults and never reloads the launch envelope.

Commit mode is receipt-backed because the client may lose the response after successful publication. Retrying the same idempotency key and source fingerprint returns the original result; a different source fingerprint conflicts.

### `config.activate`

`config.activate` does not mutate process-global state in place. It records an explicit activation intent for the current staged desired revision and returns an opaque activation ID, target/previous revisions, and required bootstrap categories. It is receipt-backed and requires that no other activation transaction is in progress.

The supervisor drains the domain host and generates a new launch envelope with a higher `bootstrapConfigurationGeneration` plus a bounded `runtimeConfigActivation` block containing the activation ID and target revision. On startup, RPC verifies that intent, revalidates the staged snapshot under the new process/bootstrap environment, and promotes it to active before reporting `Ready`. A normal crash restart whose envelope lacks that activation block always uses the prior active revision and leaves the staged candidate pending.

If the candidate cannot initialize or pass health checks, the supervisor restarts the previous runtime/bootstrap generation with a rollback block. RPC restores the previous active revision, preserves bounded failure evidence, and clears the activation intent only after rollback is durable.

### `config.discard`

`config.discard` atomically removes a staged desired candidate and makes desired equal active. It requires expected desired etag, idempotency, user authorization, and no activation already in progress. It never changes an active run or bootstrap configuration.

## Change Notification

The protocol negotiates `config.reload.v1` and adds one safe connection-level notification equivalent to:

```text
config.changed {
  desiredRevision,
  activeRevision,
  status: applied | restart_required,
  changedCategories,
  actorKind: protocol_update | file_reload | startup
}
```

The notification contains no raw diff, path, endpoint, credential reference, or secret. It refreshes UI promptly; after reconnect, `config.get` is authoritative.

Desktop application config emits an analogous internal typed channel event, not a host notification.

## Hot, Restart-Required, and Rejected Changes

### Hot for future admission

The initial hot set may include:

- default profile;
- profile add/update/remove;
- model ID and reviewed model settings/config presets;
- instructions and toolset selection;
- subagent declarations;
- provider enabled/base URL/endpoint path and credential-reference declaration;
- lazy run-scoped MCP declarations;
- environment catalog/resource allowlists when existing runs retain the old snapshot; and
- run policies that do not change process, storage, transport, or sandbox identity.

Hot means available to future admission, not mutation of an active run.

### Restart-required runtime fields

Only runtime-plane fields that stay within the immutable launch envelope and capability ceilings may be staged, for example:

- a process-global sandbox/environment-provider implementation selected from the launch allowlist;
- process-global MCP/environment adapters that cannot be rebuilt safely in place; and
- another reviewed runtime policy requiring replacement of process-global executors while leaving database, domain, state, transport, and capability identity unchanged.

Database path/identity, state or runtime-config location, execution-domain identity, transport/listener/authentication, process environment allowlist, bootstrap capability ceilings, launch schema/version, and runtime binary/channel/pin are Desktop/bootstrap configuration. Runtime `config.validate/update/reload` reports those fields as `bootstrap_owned` and never stages them. Desktop changes them through its own config/update transaction and a new launch envelope, following `06-runtime-updates-and-release.md` where applicable.

### Rejected

RPC rejects rather than stages:

- authority above the launch capability ceiling;
- native local shell when the bootstrap ceiling forbids it;
- uncoordinated execution-domain/database identity changes;
- inline credentials, tokens, authorization headers, or URL userinfo;
- renderer-provided config/filesystem paths;
- unknown provider, toolset, environment, or patch variants;
- unsafe envd endpoints; and
- shell command/argv injection.

## Session and Run Semantics

At run-admission linearization, RPC pins and durably records:

- active runtime-config generation and etag;
- profile/materialization digest;
- workspace grant identity;
- provider/tool/environment binding digest; and
- runtime binary/materialization identity.

A concurrent admission lands wholly before or after the atomic snapshot publication. It never observes a mixed config.

Reload does not mutate an active foreground run, background subagent, MCP connection, waiting HITL record, environment lease, or steer/interrupt target.

RPC persists each committed immutable runtime-config declaration/snapshot under its revision before admitting a run that references it. Durable run/materialization evidence references that revision and digest. Versioned snapshots contain declarations and secret references, never resolved credential values. They survive host failure and allow recovery/finalization to reconstruct the exact profiles, tools, MCP/environment declarations, and policy used by a referenced run.

Garbage collection is reference-aware: it retains active and desired revisions, previous rollback revisions, every revision referenced by non-terminal runs/background work/HITL/checkpoints, and a bounded completed-run compatibility horizon. A referenced revision is never overwritten in place. If an old snapshot is corrupted or unavailable, recovery fails closed with typed materialization-unavailable evidence; it never substitutes the current config.

Continuation/resume is new admission. It performs normal materialization preflight against the active config. Preserving the source snapshot is allowed only while that snapshot remains available; otherwise the result is `switch_required` or `blocked`. A same-named profile in a new generation is not silently treated as identical.

When desired and active revisions differ, current runs and new admission continue on the active revision until `config.activate` creates an explicit activation intent and the supervisor performs its fenced drain/restart transaction. An ordinary crash/restart does not activate desired state. The UI shows `restart_required` with Activate and Discard actions. Closing a window is not restart consent. Emergency authority revocation uses explicit run interruption, workspace revocation, or connection authorization controls rather than ordinary config reload.

## Workspace Registry Interaction

The one domain host manages multiple workspaces independently of config reload.

- workspace registration canonicalizes and stores private authority in the host;
- duplicate canonical roots return the existing opaque ID;
- `session.create` requires one registered `workspaceId`;
- each run receives only that session's workspace authority;
- removing a workspace blocks new session/run admission but does not rewrite historical evidence;
- active runs require explicit drain/interrupt before destructive revocation; and
- changing runtime config does not change workspace IDs.

A runtime config profile/policy update can affect future runs in every workspace. The UI therefore shows the affected categories and active/desired revisions before applying or staging it.

## Config Publication and Recovery Journal

Filesystem replacement, durable revisions/receipts, and in-memory snapshot publication are not one atomic primitive. Every `config.update`, reload commit, activate, discard, and rollback therefore uses one owner-private write-ahead config transaction record containing:

- transaction and idempotency identity plus request/source fingerprint;
- old active/desired revisions;
- candidate and previous immutable snapshot identities;
- intended new active/desired revisions;
- operation kind and bootstrap activation ID when present;
- publication phase; and
- final receipt or bounded diagnostic outcome.

The normal hot-publication order is:

1. fully validate and durably write the immutable candidate snapshot under a new non-reused revision;
2. durably publish the `prepared` transaction;
3. atomically update the desired pointer/source and mark `desired_published`;
4. atomically update the active pointer and mark `active_published`;
5. durably commit the mutation receipt and mark `receipt_committed`;
6. atomically swap the in-memory snapshot, emit notification, and mark `complete`.

No success response is written before the durable receipt. Startup acquires the config writer/recovery lock before serving initialize-dependent config state, scans the single active transaction plus immutable artifacts, verifies fingerprints, and deterministically completes or rolls back according to the last durable phase. It reconstructs the same receipt for retry and never treats an externally replaced source file alone as proof that active state changed. Temporary/orphan candidates outside any journal are quarantined and eventually garbage-collected.

Staging updates only desired after the prepared phase. Activation and rollback have separate journal phases tied to the supervisor-provided activation ID and bootstrap generation, so ordinary crash startup cannot accidentally promote desired state. Corrupt or ambiguous journal/pointer state fails closed on last-known-good active configuration and reports a bounded diagnostic; it never mixes declarations from two revisions.

## Configuration Authorization and User Presence

A closed typed renderer DTO is not sufficient authorization for a compromised renderer. The Rust backend must not automatically add host `admin` authority merely because the renderer requested a valid config mutation.

Before `config.update`, reload `commit`, staged-config activation/discard, or a security-sensitive Desktop config update, the backend independently classifies the candidate categories and requires one of:

- a native user-presence confirmation bound to execution domain, expected revision, candidate etag/fingerprint, changed categories, and one operation;
- a preinstalled managed-policy allowlist covering the same categories and destination constraints; or
- a short-lived, one-use backend grant minted by such confirmation/policy.

Provider base URL/destination changes, provider enablement, tool/capability policy, MCP/environment declarations, sandbox/shell policy, SSH routes, runtime channels/pins, and authority expansion always require this gate. The renderer cannot mint, persist, replay across revisions, or broaden the grant. For the local domain, RPC creates a 256-bit owner-private key under its launch-envelope state directory; after native confirmation the Desktop backend reads that key without following symlinks and mints an HMAC-SHA-256 token over exact execution domain, operation, expected revision, candidate fingerprint, deterministic idempotency key, UUID nonce, and bounded issue/expiry times. RPC durably consumes the nonce against the complete command fingerprint. An unconsumed expired token fails, while an already-consumed exact binding remains replayable after expiry for durable response-loss recovery; any changed binding fails. The token and key never cross renderer IPC.

Read-only safe projection may be shown without mutation authority. Side-effect-free `config.validate` and reload `validate` require the appropriate host config-inspection/admin scope and remain backend-mediated and bounded, but they do not require a candidate-bound mutation grant; they exist to produce the exact candidate fingerprint and changed categories needed for confirmation. External-file reload still requires confirmation before commit because the source may contain authority/destination changes. Desktop first requests reload `validate`, confirms the returned candidate fingerprint, then calls reload `commit` with that fingerprint, the one-use backend grant, and idempotency identity.

## Security and Persistence

- Runtime `config.update`, reload `commit`, staged activation, and staged discard require host `admin` authority plus the independent backend authorization above. Side-effect-free `config.validate` and reload `validate` require config-inspection/admin scope but no not-yet-mintable candidate grant. `config.get` returns only the safe projection allowed by its scope.
- The renderer never constructs complete admin host params. The generated Desktop manifest exposes closed safe DTOs; Rust adds expected revisions, idempotency keys, execution-domain routing, and restart policy.
- Config documents and patches have strict byte, depth, string, array, and issue-count limits.
- Managed config files use owner-only same-directory temporary files, file flush, atomic replace, parent-directory sync where supported, Unix `0600`/`0700` or equivalent Windows ACLs, no-follow checks, and file-identity revalidation.
- One writer lock and revision sequence cover every transport connection to the same host.
- Successful and failed mutations produce bounded secret-free audit evidence containing actor authority identity, old/new generation, source, changed categories, result, and diagnostic reference.
- Complete config documents and raw diffs are not session events.
- Credential resolution remains host-local at run materialization time.

## SSH Behavior

A remote RPC owns, persists, validates, and reloads its runtime config on the remote machine. Desktop sends typed patches and receives safe revisions/projections over the authenticated SSH-private RPC channel. It never downloads, edits, or forwards the remote config file or provider credentials.

Remote config reload survives tunnel loss through mutation receipts and `config.get` reconciliation. A restart-required remote candidate is staged remotely; Desktop drains and restarts only that remote domain host through its existing SSH lifecycle. One remote host continues managing all remote workspaces after reconnect.

## Current Implementation Gap

The host-side prerequisite is implemented: supervised launch and initialize are execution-domain-only; RPC owns a persistent typed workspace registry and session binding; runtime configuration has separate desired/active revisions plus self-contained immutable secret-free materialization snapshots; the six `config.*` methods, notification, receipts, generated Desktop bridge, candidate validation, HMAC authorization, atomic persistence, run snapshot pinning, and SessionRecord/RunRecord v2 provenance migration are present. Blocking filesystem/config operations are dispatched away from RPC Tokio workers, and response-flush activation prevents change notifications from overtaking the corresponding response.

Desktop now owns a strict version-1 private preference record for `theme`, `density`, and `windowCloseBehavior`. The fixed backend-selected file uses closed enums, canonical decimal revisions, exact mutation replay, same-directory atomic replacement, file and parent-directory flushes where supported, and last-known-good reload behavior. Renderer commands expose no path, unrestricted document, credential, or canonical session evidence. `keep_running` hides a closed window while preserving the one supervised host; the fixed single-instance activation route restores it. `quit` follows the coordinated application shutdown barrier.

The Settings drawer also materializes catalog/profile readiness without claiming provider credential or network readiness, changes the execution-domain default only for new runs, edits only the closed safe runtime-config projection, validates before update, and binds update/reload mutations to their exact recoverable invocation. Restart-required config candidates remain staged or discardable: a supervisor-fenced bootstrap activation transaction is still future work and remains separate from the implemented managed RPC binary selection/rollback channel. Broader Desktop-local preference fields, managed-policy grant issuance, and full cross-version release fixtures also remain. SSH is outside the Desktop roadmap. Runtime reload must never be implemented by swapping only `RpcService.config`; every long-lived derived owner consumes the retained immutable snapshot or is explicitly restart-required.

## Acceptance Gates

- Desktop config get/validate/update/reload is atomic, revision-checked, owner-private, and preserves the last-known-good snapshot on malformed external edits.
- Runtime config get/validate/update/reload passes generated IDL/server/client fixtures and has no free-form renderer JSON or raw file path surface.
- Unknown fields, stale etags, duplicate/different idempotency fingerprints, oversized patches, unsafe URLs/paths, and secret-like inline values fail deterministically.
- Fault injection before/after file flush, atomic replace, snapshot publication, receipt commit, response write, and notification proves one recoverable outcome without partial application.
- Concurrent run admission observes exactly the old or new active revision, and its durable evidence records that revision.
- Active runs, subagents, MCP clients, environments, and HITL remain pinned to their original snapshot across reload.
- Restart-required staging keeps active state unchanged across ordinary crashes; only a matching activation ID in a new bootstrap generation can promote it, while discard and failed-start rollback are durable and deterministic.
- One host manages multiple workspace/session/run bindings across reload without leaking workspace authority.
- Remote update/reload keeps config files and secrets remote and reconciles response loss through receipts plus `config.get`.
- Runtime replacement reconciles desired/active config revisions and workspace registry before reopening admission.
